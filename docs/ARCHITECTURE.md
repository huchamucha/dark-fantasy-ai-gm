# Архитектура универсальной локальной AI RPG-платформы

**Статус:** целевая архитектура  
**Версия:** 1.0  
**Язык проекта:** русский (с возможностью локализации)

## 1. Видение продукта

Создать универсальную локальную платформу для одиночных AI-RPG и визуальных новелл. Игрок запускает разные истории и сеттинги — тёмное фэнтези, научную фантастику, хоррор, детектив, постапокалипсис или пользовательский мир — на одном общем игровом движке.

Каждая история подключается как **Story Pack**. Платформа предоставляет общие механики, сохранения, AI-слой, интерфейс и медиа-систему. Первая история про Брата Эдрика, часовню и руны остаётся первым Story Pack, а не выбрасывается при переходе к универсальной архитектуре.

## 2. Принципы

1. **Local-first:** обычная игра работает локально; облачный сервер и интернет не обязательны.
2. **Single-player first:** сначала одиночная игра, без аккаунтов, мультиплеера и серверной инфраструктуры.
3. **Модульный монолит:** один backend с чёткими внутренними границами; микросервисы преждевременны.
4. **Story Pack отделён от движка:** сюжетные факты и контент не должны быть зашиты в универсальные сервисы.
5. **Движок — источник истины:** LLM предлагает интерпретацию и повествование, код проверяет правила и меняет состояние.
6. **Структурированные данные:** ответы AI валидируются; игровые изменения применяются только после проверки.
7. **Asset-first:** повторно использовать библиотеку ресурсов с постоянными ID, а не генерировать каждую картинку заново.
8. **Постепенная миграция:** сохранять работающие части текущего проекта и менять небольшими проверяемыми шагами.

## 3. Функциональные подсистемы

- Story Pack Manager: обнаружение, загрузка и проверка пакетов историй.
- Campaign Manager: создание, сохранение и загрузка отдельных прохождений.
- Game Engine: персонажи, характеристики, навыки, проверки, D20, бой, эффекты, инвентарь и квестовые условия.
- AI Layer: LLM-клиент, разбор намерений, контекст, AI-ведущий, NPC и рассказчик.
- World State: состояние мира, локаций, флаги, отношения и события.
- Memory: постоянные сведения NPC и эпизодические воспоминания с ограничением знаний.
- Media Layer: библиотека ассетов, очередь генерации изображений, TTS, музыка и эффекты.
- Frontend: визуальная новелла, диалоги, персонаж, инвентарь, журнал, карта и бой.
- Persistence: SQLite, миграции, журнал событий, автосохранение и резервные копии.

## 4. Технологический стек

| Область | Выбор на старте | Назначение |
|---|---|---|
| Frontend | React + TypeScript + Vite | Интерфейс игры |
| Backend | Python + FastAPI | API и игровые сервисы |
| Контракты | Pydantic | Валидация данных |
| База | SQLite | Локальные кампании и события |
| ORM / миграции | SQLAlchemy 2 + Alembic | Работа со схемой БД |
| Тесты | Pytest | Проверка механик и API |
| LLM | LM Studio + Qwen2.5 7B Instruct Q4_K_M | Локальный AI-ведущий |
| Изображения | ComfyUI + Stable Diffusion 1.5 сначала | Портреты, фоны, иллюстрации |
| Озвучка | Piper TTS сначала | Локальная озвучка, преимущественно CPU |
| Векторный поиск | Qdrant позднее, если понадобится | Поиск по большой памяти |
| Альтернативная БД | PostgreSQL позднее | Только при росте требований |

Не устанавливать всё одновременно. Для первого этапа достаточно текущих FastAPI, React, LM Studio и существующего хранилища с постепенной миграцией к SQLite.

## 5. Аппаратный профиль и ограничения

Целевая машина разработки: **RTX 3070 8 GB VRAM, 32 GB RAM, Ryzen 5 9600X, 100–300 GB свободного диска**.

- Qwen2.5 7B Q4_K_M — практичная исходная модель. Начинать с контекста 8–12k токенов и измерять реальное потребление VRAM.
- 8 GB VRAM — главное ограничение. Не запускать тяжёлую генерацию изображений одновременно с LLM-инференсом.
- ComfyUI начать со Stable Diffusion 1.5, умеренных разрешений 512–768 px. SDXL проверять позже в low-VRAM/offload режиме.
- Piper использовать как CPU-вариант, чтобы не занимать VRAM.
- Ввести очередь медиа-задач и кэшировать готовые изображения/реплики.
- Не планировать тяжёлую генерацию видео и крупные модели как обязательную часть первого релиза.

## 9. Story Packs

Story Pack — самостоятельный пакет контента. Он описывает сеттинг, лор, NPC, локации, предметы, квесты, стартовые сценарии, тон повествования и используемый ruleset.

Пример структуры:

```text
story_packs/
  dark_fantasy/
    manifest.json
    lore/
    characters/
    locations/
    quests/
    items/
    rules/
    prompts/
  sci_fi/
    manifest.json
  horror/
    manifest.json
```

Пример манифеста:

```json
{
  "id": "dark_fantasy",
  "name": "Dark Fantasy",
  "version": "1.0.0",
  "description": "Мрачное фэнтези",
  "ruleset": "custom_d20",
  "language": "ru",
  "assets": {
    "characters": "characters/",
    "locations": "locations/",
    "items": "items/",
    "voices": "voices/",
    "music": "music/"
  },
  "features": [
    "combat",
    "quests",
    "inventory",
    "npc_memory",
    "exploration"
  ]
}
```

Пакет контента не хранит прогресс конкретного прохождения. Прогресс принадлежит Campaign. Один Story Pack можно запускать многократно.

## 10. Библиотека ассетов

Ресурсы имеют постоянные ID и метаданные. Примеры типов:

- Character: основной портрет, эмоции, ракурсы, варианты одежды.
- Location: фоны, интерьер, экстерьер, варианты освещения.
- Creature: портреты и боевые изображения.
- Item: иконки оружия, брони, ключей и расходников.
- Audio: voice profile, музыка, атмосферные и боевые эффекты.

LLM выбирает ID ассета из переданного списка. Она не формирует произвольные файловые пути. Asset Manager проверяет ID и возвращает безопасный путь/URL. Для постоянного вида NPC использовать эталонные изображения, набор выражений/ракурсов и описание; LoRA рассматривать при необходимости. Голос NPC закрепляется через voice profile. Лицензии моделей, голосов и датасетов проверяются отдельно.

## 11. RPG-механика и разделение ответственности

**AI Layer:**
- понимает свободный текст игрока;
- предлагает тип действия, цель и требуемую проверку;
- генерирует реплики, описание сцены и реакцию NPC;
- формулирует подтверждённый результат в стиле Story Pack.

**Game Engine:**
- проверяет допустимость действия, расстояние, состояние и наличие предмета;
- выполняет бросок D20 и рассчитывает модификаторы;
- вычисляет успех/провал, урон, HP, статусы и эффекты;
- изменяет инвентарь, квесты и мир;
- сохраняет подтверждённые изменения.

Базовые механики: характеристики и навыки, D20 + модификатор против DC, критические исходы, уровни, способности, HP, броня, урон, инициатива, состояния, инвентарь и условия квестов. Конкретные параметры задаются ruleset, а не только системным промптом.

## 12. Обработка одного хода

1. Игрок отправляет свободный текст.
2. Backend загружает состояние кампании и релевантный контекст.
3. LLM возвращает структурированное предложение действия (intent), а не готовое изменение мира.
4. Backend валидирует действие и ограничения.
5. Game Engine выполняет проверки и расчёты.
6. Engine создаёт подтверждённые игровые события и обновляет состояние.
7. Изменения сохраняются в БД.
8. Narrator получает результат механики и пишет художественный ответ.
9. Frontend отображает ответ и обновлённые показатели.

Невалидный JSON, неизвестные ID и неподтверждённые изменения должны отклоняться или безопасно обрабатываться. Нельзя применять ответ LLM напрямую к HP, характеристикам или инвентарю.

## 13. Данные и сохранения

Основные сущности: Story, Campaign, Character, NPC, Location, Item, Inventory, Quest, Event, Turn, Asset.

Журнал событий хранит значимые факты: действие игрока, успешное применение предмета, результат проверки, изменение HP, изменение отношения NPC, переход локации, обновление квеста. Художественный текст хранится отдельно от механически подтверждённых фактов.

Пример события:

```json
{
  "campaign_id": "campaign_001",
  "event_type": "item_used",
  "character_id": "character_001",
  "item_id": "healing_potion",
  "target_id": "character_001",
  "result": {"healing": 6, "success": true},
  "created_at": "..."
}
```

Сначала SQLite и структурированный поиск по сущностям/тегам. Qdrant добавлять только при доказанной необходимости. Предусмотреть резервные копии и транзакционное сохранение хода.

## 14. Память NPC

- Постоянная память: личность, биография, цели, страхи, знания и стиль речи.
- Отношения: доверие, враждебность, обязательства и история контактов.
- Эпизодическая память: события, которые NPC видел или о которых достоверно узнал.
- Ограничение знаний: NPC не знает то, чего не мог наблюдать или узнать.
- Context Builder передаёт модели только релевантные сведения и недавние события, а не всю историю целиком.

## 16. Надёжность и безопасность

- Валидировать входящие данные и ответы LLM.
- Не выполнять команды, код или файловые пути, сгенерированные моделью.
- Загружать ассеты только по известным ID из разрешённых каталогов.
- Применять связанные изменения в транзакции.
- Делать резервные копии кампаний.
- Тестировать броски, проверки, урон, инвентарь, квесты, загрузку Story Pack и сохранения.
- Логировать ошибки LLM, время ответа, размер контекста и причины отказа валидации.
